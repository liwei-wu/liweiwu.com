2025 年 2 月，Andrej Karpathy 提出“氛围编程”（Vibe Coding）时，特意把它放在了一个轻松的语境里：你用自然语言告诉 AI 想要什么，接受它生成的代码，看到错误就把错误贴回去，甚至可以忘记代码本身的存在。他说，这种方式对于“一次性的周末项目”还不错。[1]

这也准确描述了我们当时愿意采用它的边界。

它已经让人看到了软件开发的一个新方向，但还不足以让我们在严肃产品里完全放手。所以整个 2025 年，我们主要使用 Cursor 这类工具，采用的仍然是一种人机混合编程：人提出意图，AI 生成或修改代码，人继续阅读代码、进入实现、判断细节，并对结果负责。

到了 2026 年初，至少对我们所做的这类应用来说，我们判断 Coding Agent 的能力和围绕它形成的工程方法，正在跨过从辅助工具到工程路径的那道线。所谓 Coding Agent，是能够自己阅读项目、修改文件、运行测试，并根据结果继续行动的编程智能体。Karpathy 在 2 月初把这种工作方式概括为 Agentic Engineering——本文暂且称之为“智能体工程”：专业开发者不再只是借助 AI 补全代码，而是组织和监督 Agent 完成工作，在放大个人执行能力的同时，保留审查与质量责任。[2] 这个名称不是某种实践突然出现的起点，更像是对一场已经发生的变化所做的总结。

也正是在这一时期，我们决定把这种方式真正用到手头的严肃产品中。

从 3 月开始，我把它当作一次有明确边界的工程实践：刻意不再把代码作为自己直接控制系统的界面，而只通过自然语言、产品文档、架构约束、运行结果和验收反馈，与 Coding Agent 一起构建包含桌面端、浏览器扩展、服务端和数据库的完整产品。换句话说，我一行代码也不写，也不读，但并没有放弃对系统的定义、验证和责任。

差不多半年的实践，并不能证明所有软件都可以这样开发。但至少在我们正在做的这类产品里，它已经成为一条可行的工程路径。这里的“可行”，不是偶尔生成一个能够运行的版本，而是进入持续规划、实现、测试、修正和迭代的完整闭环。

对我来说，真正重要的变化不是“AI 会写代码了”。这件事早已不新鲜。真正的变化是：在我们正在开发的这类应用中，实现正在从最主要的瓶颈之一，逐渐退到后面。 我相信，这个范围还会继续扩大。

当实现不再是最稀缺的部分，人的工作会变成什么？

这才是本文想讨论的问题。

## 我们所说的 AI，究竟是什么

AI 从来不是一个固定不变的名词。每一代人所说的 AI，往往指向当时计算机还没有完全做到的事情。

中学和大学时，我做机器人；研究生时，我研究计算机视觉；现在，我在做 AI 应用。回过头看，每个阶段，我们其实都在做当时当地 AI 能做的事情。许多能力一旦成熟、可靠并进入日常产品，就不再显得像 AI；而 AI 这个词，又会继续向尚未解决的边界移动。

所以，本文所说的 AI，并不泛指所有人工智能技术。它特指当前一条重要的技术路线：以大语言模型为核心，以 Coding Agent 为代表，让机器从自然语言中理解目标、调用工具、执行任务并根据反馈反复修正。这条路线可能继续通向更通用的 Agent，甚至在有限条件下形成能够从反馈中改进自身的系统。不过，那是未来的方向，不是本文论证所依赖的既成事实。

眼下已经发生的事情是：对越来越多的软件作者而言，自然语言正在成为表达意图的一层新的上层语言。

## 代码正在成为中间产物

计算机的发展史，可以看作一部不断增加抽象层的历史。

人们先用开关和插线操作机器，后来有了机器码、汇编语言和高级语言。每增加一层抽象，机器的复杂性就被向下封装一层，人也可以离自己的意图更近一点。

Coding Agent 又增加了一个新的抽象层。

它有些像一台超级编译器：传统编译器把高级语言转化为机器指令，Coding Agent 则把人的意图不断展开为产品、界面、数据、服务和代码。

当然，这只是一个比喻。传统编译器处理的是形式明确的语言；Coding Agent 面对的却是含混、残缺、有时彼此矛盾的人类表达。它不是把一句话确定地翻译成一个结果，而是需要在理解、规划、执行、运行和验证之间反复循环。

因此，自然语言并没有简单地“取代”编程语言。更准确地说，对人而言，自然语言和文档正在成为意图层的主要表达；代码则越来越像由 Agent 生成和维护的实现载体。

这也改变了我们应该把什么写清楚。

过去，文档常常只是代码的说明；今天，在我们的实践里，这层关系开始倒过来：代码越来越多地依据文档被生成和验证。产品为什么存在，系统怎样工作，哪些边界不可突破，怎样才算完成——这些过去容易被放在代码旁边的内容，正在成为人真正需要维护的源头。

不再亲手写代码，并没有降低表达的要求，反而提高了它。

一个含混的想法，过去可能会卡在漫长的实现过程中；现在，Agent 会迅速把它变成一个能够运行的错误系统。实现越快，没想清楚的地方就暴露得越快。

AI 并没有免除思考。它只是让人更难用实现的忙碌，掩盖思考的含混。

## “纸和笔”的下半句

2025 年，王坚把 AI 比作人类“新的纸和笔”：它不是思想本身，而是人类思想的一种延伸。[3] 我很认同这个比喻。

它甚至带着一种有趣的历史对称。1948 年，图灵曾设想，一个人如果拿着纸、铅笔和橡皮，严格遵循一组规则，他的行为就可以被看作一台通用机器。[4] 那时，人们借助纸和笔来解释人怎样模拟机器。近八十年后，方向似乎反了过来：机器正在成为新的纸和笔，帮助人把意图展开为可以运行的世界。

这个比喻也让我想起自己读大学时的生活。除了睡觉，我大概有三分之一的时间都在折腾软件：安装操作系统，配置环境，学习新的工具，再做一些自己想做的演示。那个过程当然有乐趣，但我也常常把更多时间花在准备创造，而不是创造本身。就像一个画家，总在寻找纸张、制作颜料和修理画笔。

我说 AI 是新的纸和笔，并不是因为它无所不能。恰恰相反，纸和笔从来都不是万能的。

纸不会自动写出小说，颜料不会自动画出好画，相机也不会自动拍出好电影。工具降低了表达的成本，却没有替创作者决定什么值得表达。Coding Agent 比纸笔主动得多：它会提出建议，会执行任务，也会在一定范围内作出选择。但只要它还不能为作品的目的和后果承担责任，它就没有因此自动成为作者。

把 AI 比作新的纸和笔，并不是我的首创。真正令我感兴趣的，是这个比喻的下半句：

如果有了新的纸和笔，我们需要什么样的艺术家？

## 艺术正在向上移动一个抽象层

“程序员是艺术家”同样不是一个新说法。

1974 年，Donald Knuth 就发表过《作为艺术的计算机程序设计》，讨论编程为何需要知识、技巧、创造力，也会产生具有美感的对象。[5] 2003 年，Paul Graham 在《黑客与画家》中进一步提出，黑客与画家都是“创造东西的人”；对软件创造者而言，计算机就像颜料之于画家、混凝土之于建筑师，是一种表达媒介。[6]

所以，AI 并不是让程序员第一次成为艺术家。

它改变的是艺术发生的层级。

过去，程序员的艺术很大一部分发生在代码内部：一个算法是否精巧，一组抽象是否简洁，一个系统是否以最少的结构容纳了足够的可能性。那是一种只有深入实现才能体会的美，也不会因为 Agent 出现而失去价值。

但当越来越多的实现工作下沉给 Agent，人的创作重心就会向上移动。软件的艺术将更多地发生在整个作品上：它选择了什么问题，理解了怎样的人，建立了什么秩序，舍弃了哪些可能，怎样回应用户，又以什么方式进入人的生活。

这种发生在产品和体验层的艺术当然早已存在。变化在于，当实现不再占据大部分注意力，它更有可能成为更多软件创造者的主要工作对象。

代码的优雅仍然重要，但它不再是软件之美的全部，甚至不再总是人直接创作的部分。人与 AI 共同完成的，也不应只被看作一堆正确运行的代码，而应被看作一个完整的软件作品。

这就是“新的艺术家”真正指向的变化。

如果用现有的职业语言近似描述，他有些像产品经理和架构师的混合体。产品经理追问做什么、为谁而做；架构师追问系统怎样长期成立、边界和约束在哪里。但这两个称呼仍然不够。新的软件艺术家还需要审美、同理心、取舍能力，以及对整体结果的责任。

这里的“艺术家”不是一种更高贵的职位，也不一定是某一个人。它是一种对完整作品负责的作者角色，也可以由一个跨职能团队共同承担。

技术解决“怎样把一件事做成”，艺术决定“什么值得被做出来，以及希望人怎样感受它”。这不是一条绝对的分界线——“做什么”和“怎样做”从来都会相互塑造——但它指出了软件创造正在发生的重心转移。

工程保证作品能够可靠地存在；艺术决定它为什么存在，以及怎样进入人的生活。

## 工程没有消失，责任也没有

新的艺术家并不是只需要提出一个好点子，然后等 AI 把剩下的事情做完。

纸笔的普及没有让写作变得不需要训练；相机的普及也没有让摄影变得不需要判断。Coding Agent 降低了实现的门槛，却没有让复杂系统里的架构、安全、性能、质量和维护自动得到解决。

我不读代码，也不意味着我放弃了工程控制。控制点只是发生了变化：从逐行检查实现，转向明确系统目标、架构原则、数据边界、权限模型、测试标准、可观测性和验收结果。AI 可以参与其中每一项工作，但最终必须由人判断这些约束是否充分、证据是否可信，以及这个结果能否被交付。

有些领域——例如基础设施、安全关键系统和底层软件——仍会长期要求人深入代码，甚至比过去更需要少数真正理解底层的人。新的抽象层从来不会消灭下面的层。高级语言没有消灭汇编，云计算也没有消灭操作系统。它只是让大多数创造者不必在每一次创造中重新穿过所有底层。

更强的工具也会带来更大规模的平庸。实现成本降低以后，我们很可能先得到更多重复、粗糙、没有真实需求的软件。纸和笔不会自动带来文学，Coding Agent 也不会自动带来软件的文艺复兴。

AI 没有消除稀缺性，它只是转移了稀缺性。

过去，软件生产的大部分稀缺性集中在编程能力、工程资源和实现时间上；当这些成本继续下降，问题判断、产品直觉、系统认知、审美、对人的理解，以及为后果负责的意愿，就会变得相对更加稀缺。

当“怎样做成”越来越便宜，“究竟做什么”就会变得越来越昂贵。

## 从代码的作者，到软件作品的作者

Bret Taylor 曾转述并赞同 Arya Asemanfar 的一个准确概括：AI 可以替你起草，但你仍然是作者。[7] Addy Osmani 则把开发者的新角色描述为架构师和战略制定者。[8]

作者并不等于亲手完成作品中的每一个动作。建筑师不亲手砌下每一块砖，导演也不操作片场里的每一台摄影机。但他们必须知道作品要成为什么，必须能够判断它是否成立，也必须对最后的整体负责。

软件正在发生同样的变化。

过去，我们常常用“谁写了代码”来识别软件的作者。以后，作者身份将越来越取决于另一组问题：谁定义了问题，谁建立了约束，谁作出了关键取舍，谁判断作品是否完成，又由谁承担它进入现实世界之后的后果。

这还可能改变软件的经济单位。过去，只有足够多人共享的需求，才值得被开发成一套软件；当实现成本大幅下降，一个团队、一个家庭，甚至一个人的特殊工作流，也可能值得拥有自己的软件。未来未必人人都要成为程序员，但更多人可以成为软件的作者。

我从三年前开始创业，2025 年注册了“深度飞轮”。过去差不多半年的实践，不是这段旅程的起点，也没有证明我从一开始就想对了一切；它只是让一个长期没有改变的方向变得更清楚：我们选择做应用，因为只有应用会把模型的能力交给真实的人，并由使用、信任和付费给出最诚实的反馈。至于怎样让这种反馈进入下一轮创造，那是另一篇文章的话题。

对这篇文章来说，结论可以更简单一些。

AI 把大量实现工作向下推，也把人的责任和创作重心向上推了一个抽象层。程序员将不再只做代码的作者，而会越来越成为软件作品的作者——这就是我所说的“新的艺术家”。

新的纸和笔已经出现。但新的文艺复兴并不会因此自动到来。它不取决于 Agent 能生成多少代码，而取决于我们是否有判断力，也是否愿意承担责任，回答一个比“怎样做成”更困难的问题：

什么值得被创造，又希望人怎样感受它？
